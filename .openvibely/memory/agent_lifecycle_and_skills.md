OpenVibely has lifecycle-agent and skills behavior guided by `runbooks/agent-lifecycle-hooks-and-skills.md`; verify current source before relying on exact behavior.

Naming direction from thread `92ee0d2d21ca6a15fa1b4d5249cbae11`, reinforced by thread `c506bba881d7f915b111d6252a1e2766` on 2026-05-25: the built-in system agent is Skill Curator, with clean `skill_curator` identifiers and bundled paths. The maintenance skill is Maintain Skill Library, with clean `maintain_skill_library` identifiers. Bundled Skill Curator skills should avoid saying “agent” where they mean “skill.” Because the feature is unreleased and the user is the only current user, do not preserve compatibility/fallback aliases or old paths; verify source and keep declarations, seeds, migrations, and tests on the clean names.

Skills and catalog storage:
- Skills are implemented around a filesystem catalog in `internal/agentskills/`, with global/project roots, project-over-global precedence, frontmatter/rendering support, and prompt-safe runtime tools such as `skill_view`, `skills_list`, `agents_list`, and optionally `agent_view`.
- Skill handles and paths must remain constrained to indexed catalog entries rather than model-supplied paths.
- Standalone skill catalogs and agent-owned skill catalogs both merge global and project roots with project definitions winning on duplicate skill keys. Standalone skills live under `<root>/skills/<skill_key>/SKILL.md`; agent-owned skills live under `<root>/agents/<agent_key>/skills/<skill_key>/SKILL.md`. Assigned-agent tasks should use the assigned agent's merged agent-owned skill catalog, not the standalone top-level skills catalog.
- Built-in/global agents and skills are synced under the app/config root for the active runtime mode, while project-scoped agents/skills live under `<project_root>/.openvibely/agents/...`. Local web/server and desktop mode should share the same global app/config root, `$HOME/.openvibely` by default unless env overrides apply, rather than maintaining separate global-agent directories. Docker/hosted deployments should keep using their explicit persisted app-data roots such as `/data` when configured.
- Product expectation from thread `146f0fe5bfa51092a538981be6ae771c` on 2026-05-26: agents are global by default and should remain reusable across projects without per-project duplication. Global agents such as Skill Curator and user agents like Claudia/Cindy should live in the global app/config agents directory, not a project's `.openvibely/agents`, unless explicitly project-scoped. If the agent editor exposes scope values such as global/project, the selected scope should correspond clearly to where the agent and its skills live on disk; avoid ambiguous user-facing values like "unspecified" unless it is only legacy/internal metadata and is explained or hidden.
- Product intent, clarified on 2026-05-23, is that the on-disk index is authoritative for catalog discovery and is LLM-owned end-to-end after seeding: `<agents_root>/AGENTS.md` lists agents at that root, `<agents_root>/<agent_key>/SKILLS.md` lists that agent's skills, and `<agents_root>/<agent_key>/skills/<skill_key>/SKILL.md` remains the skill body.
- The router agent, `agents_list`, and `skills_list` should trust on-disk indexes rather than doing per-turn filesystem scans.
- For assigned-agent tasks, route-hook context may still render `available_skills` from the assigned agent's authoritative `SKILLS.md`, and scoped `skill_view` may inspect those listed agent-owned skills. Route-hook runtime skill tools must inspect the same assigned-agent scoped catalog used for `available_skills`; do not expose a `skills_list` view of top-level standalone skills when those skills would later be rejected by scoped selection.
- Built-in shipped agents should ship default embedded index files through the existing `builtinskills` embed/sync path. Sync should overwrite bundled `SKILL.md` bodies as app-owned source of truth, but only create bundled `AGENTS.md`/`SKILLS.md` index files when missing because the LLM/user owns them once on disk.
- There is no separate first-run marker for indexes: destination file presence is the initialization signal, so deleting an index lets startup reseed the embedded default while app upgrades do not push new defaults over existing LLM-maintained indexes.
- Do not reintroduce deterministic index rebuild code, a runtime index generator, or a `rebuild_indexes` runtime tool.
- `agent_manage`, `skill_manage`, and maintainer instructions should rely on mutation tools for required catalog mutations and minimal per-agent skill-link maintenance where supported; scoped file edits are for `AGENTS.md` updates when needed and narrative/root-overview polish, not redundant manual minimal-link edits.
- If indexes are absent at startup, startup should only create directories; the per-turn catalog should be empty for that scope, `<available_skills>` should still be emitted with no indexed skills, routing has no indexed agent/skill to select, and `skill_view` should remain constrained by the empty catalog rather than reading arbitrary paths.
- Missing indexes should degrade agent behavior but not crash or trigger deterministic regeneration.
- Bootstrap code such as `agentskills.EnsureAgentsRoot(root)` should only ensure directories exist and should not rebuild or deterministically edit `AGENTS.md`/`SKILLS.md` outside the built-in first-run seed path.

Agent and skill mutation behavior:
- As of 2026-05-24, built-in Skill Curator instructions expect `agent_manage`/`skill_manage` to maintain the required minimal per-agent skill-link index automatically; do not tell Skill Curator to make redundant scoped-file edits for those minimal links.
- Scoped `read_file`/`edit_file` tools remain appropriate for `AGENTS.md` updates when needed and for narrative polish/root-overview edits that preserve existing active skill links.
- `observe_task_for_learning` runs as `skill_curator` after task completion and should explicitly inspect project `.openvibely/agents/` and global `agents` roots for new or changed `SKILL.md` files missing from `AGENTS.md`/`SKILLS.md`.
- Product direction from 2026-05-24: `observe_task_for_learning` should behave like a forked reviewer implemented as a lifecycle hook, receiving only the actual compacted backend LLM chat-context JSON/task conversation snapshot and using a prompt that reviews that conversation directly rather than relying on lifecycle metadata, execution summaries, diffs, changed-file lists, prewritten summaries, or other task artifacts. The hook should reuse the task-managed compacted message context, such as `transcript.Messages` when that is the backend request context, instead of inventing a separate post-hook truncation/capping policy. Adapter glue such as `llm_chat_context.go`/`ChatContextFromNormalizedRequest` should only translate normalized request `ChatHistory` plus the current assistant turn into the lifecycle `ChatContext` contract; it should not reload DB history or impose a second truncation policy. If `llmcontracts.ChatContext` already has the lifecycle payload shape, avoid retaining a redundant wrapper such as `LifecycleConversationTranscript`; pass the chat context directly as `conversation_transcript` unless a verified package-cycle or schema-decoupling need exists. Do not pass the whole persisted thread or bulky execution artifacts into lifecycle LLM input; past failures exceeded provider input limits by accidentally sending tens of millions of characters.
- Before saving learning from `observe_task_for_learning`, the Skill Curator reviewer should inspect existing agents/skills with the list/view/manage tools as needed so it can avoid creating duplicate or already-covered learning.
- `observe_task_for_learning` instructions should treat the absence of a suitable existing agent/skill as a reason to create durable coverage when the learning is reusable; do not let "no existing suitable agent" become a no-op rationale.
- As of 2026-05-24 source inspection, `observe_task_for_learning`/`LLMHookInvoker` currently calls `CallAgentDirect` as a single prompt/response with no tool loop and no `agent_manage`/`skill_manage` tools, so it cannot actually create agents or skills during the hook; it can only return the structured learning-summary receipt. The better Skill Curator design is a hidden multi-step reviewer session that can inspect files and call tools, with the structured JSON used only as the final receipt.
- Agent root `SKILLS.md` should be the authoritative place for agent-level metadata used by the Agents page, lifecycle hooks, and normal task-thread agent loading, including tools, permissions, lifecycle hooks, and related declaration data; avoid duplicating metadata in Go seed code when it can be derived from the root declaration.
- Agent root `SKILLS.md` should also be a Markdown overview/index that links to the agent's actual skill files, such as `skills/<skill_key>/SKILL.md`; Skill Curator instructions should require maintaining those links when creating, managing, or reviewing agents.
- Repeated Skill Curator or `after_complete` skill-creation passes must update `SKILLS.md` idempotently by preserving existing skill links and upserting new ones rather than rewriting the overview in a way that drops earlier entries.
- Skill consolidation is a maintenance/mutation action: merge or retire duplicate skills only when the Skill Curator session actually has the needed file/mutation tools and preserves the affected indexes. A post-task hook with only an output contract should recommend consolidation rather than claiming it performed one.
- Do not use agent root `SKILLS.md` as the canonical prompt container. Agent prompts/instructions should be driven by the appropriate skill `SKILL.md`; the root file may contain a human-readable overview, but labels in the app/editor should not imply the root overview is the agent prompt.
- Product/UI direction from thread `a4bc221f3eb34aacdefb48fc65e614f4` on 2026-05-25, reinforced by threads `6690423231e8b8111505ff9729625161` and `e1ba04cb5bfffcfda3bff53af0f384bd` on 2026-05-26: the agent create/edit dialog should align with the new on-disk agent-owned skill flow, not the older embedded generated-skill model. It should let users see/manage actual agent-owned `SKILL.md` files and `SKILLS.md` overview/index metadata, avoid implying root `SKILLS.md` is the agent prompt, keep lifecycle editing focused on real hook slots rather than exposing `task_mode` as a normal user-authored hook, and avoid legacy Routing-tab/hint fields in favor of live concepts such as `selectable_as_primary` and selected/default skills. In the dialog, label the agent-owned skill area simply as "Skills"; "Agent-Owned Skills" implies the wrong ownership model. Avoid exposing Model Defaults JSON editing in the Advanced tab for now because it encourages model-behavior overrides. Default `selectable_as_primary` to enabled for new-agent create flow and legacy conversions unless a source declaration explicitly says otherwise. Fold permission/default tool policy into the Lifecycle Hooks tab instead of presenting a separate Permissions tab, because lifecycle hook configuration and its allowed/default tools should be understood together.
- Context from thread `606c32bfa24477fea72a276d47b882b4`, updated by thread `1f8b240a06ef166aac9884135be56a4f` on 2026-05-26: “Legacy Embedded Skills” in the agent-owned skills UI refers to older DB-backed skills stored directly on the agent record, such as `models.Agent.Skills`. These are compatibility data and are distinct from routed agent-owned skills stored on disk under `agents/<agent_key>/SKILLS.md` and `agents/<agent_key>/skills/<skill_key>/SKILL.md`; the new assigned-agent skill router should use the on-disk agent-owned catalog, not legacy embedded DB skills. Product expectation is to auto-convert legacy embedded skills into the new on-disk agent-owned skill layout and clear/hide the legacy concept after successful migration, rather than preserving it as an active separate UI category.
- Source inspection from thread `ae15cc7e18035b956dc1d61220c3851b` on 2026-05-26 found that legacy DB-backed agents can exist without corresponding on-disk entries under `agents/AGENTS.md` or `agents/<agent_key>/...`; root-declaration sync imports/updates DB rows from the on-disk catalog but does not automatically materialize every DB legacy agent to disk. Distinguish DB legacy agents such as user-created/imported historical agents from the on-disk agent catalog before assuming a missing file is data loss.
- Product direction from thread `e1ba04cb5bfffcfda3bff53af0f384bd` on 2026-05-26, reinforced by thread `a93bfcd7f618bce58f79241ca8c7ff61`: legacy DB-only agents should be safely exported/materialized into the global on-disk `agents/` catalog during storage/catalog migration, so historical agents appear alongside filesystem-native agents instead of remaining hidden DB compatibility records. Global skills need no release migration path because they were not released before this storage/catalog change.
- Product feedback from thread `0d126eacdb95afc9a4637f989ba58555` on 2026-05-26: when materializing legacy DB agents to disk, do not create user-visible keys with a `legacy_` prefix from invalid stored keys. Prefer a clean slug from the agent display name, such as Cindy -> `cindy`, and use IDs only as a last-resort fallback.
- Review context from thread `37e10e9dd0cbc388561b9441347024e8` on 2026-05-26: legacy-agent materialization needs special care for data preservation and idempotency. Discovering an existing on-disk agent file during list-time materialization should not accidentally rewrite DB state or persist a stale in-memory copy; verify importer/root-declaration sync behavior before assuming disk discovery is a no-op.
- Agent/hook declarations listing tools are not sufficient by themselves; lifecycle execution must actually register those tools in the runtime context used for the LLM call. For detached `after_complete` runs, verify the context preserves or rebuilds lifecycle runtime tools such as `agents_list`, `skills_list`, `agent_manage`, and `skill_manage` instead of starting from a bare `context.Background()`.
- Lifecycle hooks and primary task-thread agent runs should both consume the declared tool/permission metadata from the loaded agent/skill definition, so hook agents and explicitly/route-selected primary agents get the same allowed-tool configuration semantics.
- From thread `7d816e2338868e6ff5d584443d1d4a4f`: `observe_task_for_learning` is a Skill Curator `after_complete` hook, not an execution as the task's assigned primary agent. Assigned-agent task context should not implicitly grant this hook authority over agent-owned skills or agent definitions; mutation requires explicit lifecycle runtime tool grants for the hook owner, and standalone `skill_manage` is not the path for managing agent-owned implementation skills.
- Product direction from threads `0812255eb53924bcf112a288924d5b53` and `0bdc199e512b23d72900615bcb3b83ea`, reinforced by thread `197bf5ebf8e930561cdec8b11a76e73e` on 2026-05-25: if Skill Curator is allowed to improve an assigned agent after task completion, use a separate server-scoped agent-owned skill mutation path, exposed in this design as `agent_skill_manage`, rather than `skill_manage`. The model should not choose an arbitrary target agent; the server should resolve the current task's assigned agent, allow the tool only when a task had an assigned agent, and constrain edits to that assigned agent's selected/owned skills unless a clearly agent-specific new skill is being created.
- For Skill Curator learning placement, keep reusable cross-agent improvements in standalone skills and reserve assigned-agent skill/definition updates for behavior specific to that assigned agent's role, purpose, private workflow, or selected agent-owned skill. Product feedback from thread `4f019ceac5d9ac7e3f17943e6bf7ca47` clarified that the hook should know the selected/assigned agent and what that agent is for, because this is a key signal for classifying where created skills should be scoped. Hook context and tool descriptions should label provenance explicitly, such as assigned agent identity, assigned agent purpose/description, selected agent-owned skills, selected standalone skills, and write policy; do not rely on the LLM inferring scope from filesystem paths like `agents/foo/skills/bar` versus `skills/bar`. If uncertain, prefer standalone skill updates or return a review/proposed-change outcome rather than mutating; avoid bulk-copying standalone or unrelated skills into an agent.
- Ordinary task agents using `agent_manage`/`skill_manage` may lack scoped index-file access, so tool descriptions should tell them to update indexes only when they have access; otherwise they should mention created/changed skills in the completion summary for the Skill Curator after-complete hook to index.
- The Skill Curator should be able to create and maintain both global and project-local agents/skills, autonomously or via user instruction.
- Do not block global-scope `agent_manage`/`skill_manage` just because an earlier scoped-files configuration only covered project `.openvibely/agents`; authorize the Skill Curator with scoped access to both global and project agents roots when both scopes are intended. The `globalSkillRoot`/global agents root concept is used across catalog discovery, mutation, and runtime tool scoping, so do not remove or collapse it into the project root without a verified replacement for every call site.
- When lifecycle/Skill Curator flows generate an agent, declarations must include the explicit frontmatter `kind` expected by the catalog/manager, such as `openvibely.agent_skill`; missing `kind` blocks creation.
- Product feedback from 2026-05-25: standalone skill creation/manage/review flows should not require or display large empty legacy agent/routing/permission/model scaffolding. Keep standalone skill declarations to the fields actually needed by the current catalog/manager schema, and verify source before relying on any example frontmatter. Compact standalone skill selection metadata such as `routing.triggers`, `routing.priority`, and `routing.description` is distinct from removed legacy agent-routing hint fields and should not be removed just because the old Routing tab/plumbing was removed.
- Product feedback from 2026-05-25: prompts for skill creation/review/maintenance should express storage boundaries abstractly as what belongs in the current artifact, such as reusable execution guidance versus contextual notes, rather than directly and repeatedly contrasting "memory" with "skills".
- Verify persisted allowed-tool configuration and the Agents page/editor state, not only model output or database rows. A created agent can look successful while having no allowed tools enabled if tool permissions are not explicitly derived and saved with the agent.
- Do not treat ad-hoc project-scoped agents/skills created during test runs as built-in seeded product behavior. Distinguish runtime/user-created filesystem artifacts from embedded built-in skills or migrations.
- A natural QA pattern for autonomous Skill Curator skill creation is to give a repo-specific discovery task with reusable workflow value, then a follow-up repeating the pattern. Good tasks involve discovery, repeated commands, repo-specific gotchas, and future utility; examples include a tiny `.templ` change requiring regeneration/validation or lifecycle-hook validation. Skill creation is judgment-based and may correctly create nothing for trivial or already-covered work.

Lifecycle hooks and scheduling:
- Lifecycle hooks are implemented around `internal/lifecycle/` and wired into task execution/server setup. Important design concepts include `route_task`, `before_run`, `after_complete`, `scheduled`, task-mode bookkeeping, blocking versus non-blocking hook execution, idempotency/audit rows, recursion prevention, and strict validation of hook types and tool access.
- `task_mode` is the lifecycle slot/row for the primary active task execution: current source inspection from thread `13cba40980f1692d15ba74bc53b6f1a3` found the normal task model call is not invoked through the same `runLifecycleSlot(task_mode)` hook path, even though it is represented as the assigned/default effective-agent execution between preparation and post-completion hooks. Treat it as internal bookkeeping or advanced/debug visibility rather than a normal user-authored hook like `route_task`, `before_run`, or `after_complete`.
- The `route_task` hook is a separate LLM routing decision that consumes the prompt-safe agent index and may switch/continue/clarify; it should not be confused with catalog/index generation itself.
- Lifecycle hook skill resolution should be scoped to the hook owner only. If the hook owner's skill is missing, fail rather than falling back to the task turn's selected/available skill catalog; with assigned-agent scoped catalogs, fallback can accidentally run an assigned task agent's same-named skill such as `route_task` as the lifecycle hook implementation.
- As of 2026-05-25 source inspection, router-selected skills use a plural selected-skills output contract with a JSON `skills` array. Multiple skills may come from one router result and should be preserved in lifecycle storage, summaries, and task context, but multiple route-hook outputs are not merged; the lifecycle selection chooses the highest-confidence valid router output and uses that result's entire `skills` array.
- Routing/effective-mode reviews should explicitly verify what happens when multiple agents appear selected by UI or hook output. Tool permissions should come from one primary agent/effective mode only; do not merge permissions across agents or introduce multi-agent task execution unless explicitly re-designed.
- As of 2026-05-25 product direction, ordinary tasks may intentionally have no assigned primary agent. The task/detail agent selector may offer a blank/no-agent choice, but UI copy should label it as no assigned agent or skill-routed/default task behavior rather than an "Auto Agent" product-level routing mode.
- Product direction from thread `b82cc86ea19765d469045697f0e9bedc`, reinforced by thread `de172ffae1b4dad16d344a5795aca48d`: the legacy Routing tab and unused routing-hint declaration/model/persistence plumbing should be removed as a long-term cleanup unless a field is verified active in the current flow. Current routing-related UI should focus on `selectable_as_primary` and selected/default skills; legacy hint metadata such as `good_for`, `avoid_for`, thresholds, follow-up preferences, and fallback/clarification settings should not be presented as important user-facing configuration unless source verification shows live runtime behavior. Preserve `selectable_as_primary` as the flag that controls whether an agent can be selected as a primary task agent.
- Any task with an explicit `AgentDefinitionID`/assigned primary agent should skip the skill router and use that agent's curated/default or manual skill selection. Skill routing must not override deliberate agent assignments.
- In task detail UI, display the selected primary task agent from the persisted task assignment/effective mode. A lifecycle activity row such as `route_task — skill_curator` may identify the lifecycle hook executor rather than the routed primary task agent, so do not infer the selected agent from hook-executor rows.
- If task detail UI appears to stop showing lifecycle events after six rows or after an older timestamp, first check the lifecycle activity query/render limit and whether reruns/follow-ups are associated with the same task before assuming lifecycle execution stopped; persisted lifecycle rows may continue beyond the visible recent-activity slice.
- Lifecycle/task detail visibility should make router-selected skills visible in the lifecycle task tab so users can see which skills were selected for the run, rather than only exposing hook executor rows or backend routing internals.
- A lifecycle hook `OutputContract` constrains the final structured hook result stored/validated by the lifecycle system, not the agent's freeform reasoning, tool use, or working notes during the session.
- When debugging what the Skill Curator or another lifecycle agent actually said or did, inspect raw hook output, execution logs, lifecycle rows, and task records before inferring from summaries or visible UI state.
- Logs alone are not sufficient to debug lifecycle decision quality, especially for Skill Curator learning review. Lifecycle execution records should store a structured trace with the rendered/redacted prompt snapshot, tool calls grouped by execution ID with args/results/errors, raw final model output, validated contract JSON, duration, model, and provider so reviewers can reconstruct why an agent created or rejected learning.
- For `observe_task_for_learning`, the final result should be a JSON receipt summarizing observations plus created/updated skills or agents and follow-up recommendations; if nothing changed, return the same contract with empty arrays.
- If `observe_task_for_learning` or another lifecycle hook with `OutputContract` fails validation with `invalid JSON` and an unexpected first character such as `I`, inspect the raw hook output for prose and enforce JSON-only final output for the configured contract rather than treating the hook as a successful freeform response.
- For `route_task` aggregation, collect hook results, ignore invalid modes and agents with `selectable_as_primary=false`, choose the valid `switch` with highest confidence, and otherwise keep the current agent. Maintenance/system agents such as Skill Curator should be blocked through `selectable_as_primary=false`, not hardcoded name checks.
- `selectable_as_primary=false` means the router must not auto-select that agent as the primary task agent. It should not be an execution-time ban: explicit user/API assignment, scheduled tasks, and other deliberate invocations may still run that agent as the main task execution agent.
- Product direction after 2026-05-23 feedback, reinforced on 2026-05-24: avoid maintaining a second scheduling system for lifecycle hooks when scheduled agent work can be represented by the existing app task scheduler assigning agents. Do not declare app-owned scheduled maintenance as a `scheduled` section inside a skill YAML/frontmatter unless that skill truly controls lifecycle scheduling semantics.
- Built-in skill library maintenance, such as “Review and maintain skill library,” should follow the same visible scheduled-task pattern as the default memory consolidation task: create/repair a built-in scheduled task and let the normal scheduler/worker path run it.
- System-agent scheduled tasks should respect their explicit assigned agent and selected/manual skill configuration instead of running ordinary `route_task` skill routing. Any `PrepareLifecycleTurn` special case that selects `skill_curator/maintain_skill_library` should be treated as a narrow scheduled-maintenance bridge, not a precedent for enabling router-selected skills for system agents.
- As of 2026-05-25, `System: Memory Consolidation` is a temporary special scheduled-task case because `System: Skill Curator` has not yet been converted into a real on-disk agent; do not redesign it solely to fit scheduled Skill Curator routing without re-verifying current product direction.
- Source inspection from thread `42a62c0b9f1c66bb8d5dd47913adc9e2` on 2026-05-25 found that assigning a primary agent to a normal task does not automatically inject all agent-owned skill bodies. Agent-owned skills are read only where code explicitly resolves them, such as lifecycle hook skill-key resolution and the scheduled Skill Library Maintenance special-case context.
- The built-in scheduled maintenance task should remain in place and use the Skill Curator agent with the `maintain_skill_library` skill for reviewing, maintaining, and consolidating skills and their on-disk indexes. The scheduler/worker path should select that agent+skill and let the loaded Skill Curator declaration drive runtime tool grants; avoid worker-side special cases that hard-code maintenance tools instead of consuming the agent/skill metadata. Scope this scheduled task to skill maintenance, not broader agent creation/maintenance, and grant only the needed skill-maintenance tool access such as `skill_manage` rather than broad agent mutation.
- Skill-library maintenance may inspect agent namespaces and available skills for context, but should not create, edit, archive, route, reassign, or otherwise manage standalone user-controlled agents. It should also avoid memory changes during maintenance runs and prefer small, evidence-backed skill consolidation or `SKILL.md` instruction updates.
- `maintain_skill_library/SKILL.md` is the scheduled/normal maintenance skill, while the post-task `after_complete` hook may be `observe_task_for_learning`; if consolidation is expected immediately after completion, put that behavior in the observe hook or have it trigger/recommend the scheduled maintainer explicitly rather than assuming the maintainer skill runs as the post hook.
- Prefer modeling `when_slot=scheduled` maintenance as normal scheduled tasks or task-template/configuration that runs through the usual task lifecycle, unless a runbook explicitly requires invisible background hooks.
- For Skill Curator filesystem access, reuse generic `scoped_files` runtime tool config rooted at relevant agents directories rather than introducing a bespoke tool package.
- Lifecycle direct-call scoped-file setup must pass absolute directories for extra scopes such as `global_agents`; resolve configured/built-in agent roots before constructing `ScopedFiles` extras so hooks like Skill Curator do not fail during tool preparation.
- Verify current source before relying on whether `internal/lifecycle/scheduler.go` still exists or is wired separately from `internal/service/scheduler_service.go`.

End-to-end wiring expectations:
- Lifecycle/skills work is incomplete unless it is wired end-to-end: build the skill catalog for each task turn, resolve hook skill bodies, call `route_task` and effective-mode resolution before LLM execution, register read/write runtime tools on relevant LLM calls, ensure created agents/skills appear in the agreed filesystem catalog/directory structure, execute scheduled bindings, and provide enough operational logging to debug new lifecycle/skill behavior.
- Past lifecycle/skills audits found easy-to-miss wiring gaps to re-check before declaring completion: UI tabs or client calls without backend handlers, hook outputs computed but not merged into model prompts, route/effective-mode decisions captured but unused, runtime tools registered with nil/unwired dependencies, and write-side skill/agent mutations not visible until the intended refresh boundary.
- Design intent is to route tasks, inject memory before work, run task-mode behavior, update memory after completion, and maintain reusable agents/skills without hardcoding memory-specific behavior into task execution.
