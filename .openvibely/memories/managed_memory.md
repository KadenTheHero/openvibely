title: Managed Memory

OpenVibely managed memory is model-backed, tool-driven, project-scoped, and stored under the selected project's repo-local `.openvibely/memories/` directory. The directory stays flat: `MEMORIES.md` is the compact index and focused top-level topic files hold durable context. Do not recreate old `user/`, `feedback/`, `project/`, or `runs/` subdirectories.

Storage and access boundaries:
- Scoped memory file tools may already be rooted at `.openvibely/memories`; if that path appears missing, list `.` before assuming memory is absent or creating nested paths.
- Memory requires a selected project with a valid local `repo_path`; do not use app-owned fallbacks such as `memory/projects/<project_id>/` or `OPENVIBELY_MEMORY_ROOT`.
- `MemoryService` owns path resolution, file storage, context building, extraction, consolidation, and DB metadata. Use existing SQLite task/chat execution history as transcript source; do not add JSONL transcript storage or unreleased layout migrations unless explicitly requested.
- Initialization is idempotent in web/server and Wails desktop modes. Startup/runtime paths may create `.openvibely/memories/` and `MEMORIES.md` when missing; topic files should be created only by explicit durable-memory writes.
- Managed-memory tools must be scoped to the memory directory and reject traversal, absolute paths, and symlink escapes. Keep memory-specific policy in prompts/config rather than generic scoped-file enforcement.

Content boundaries:
- Save distilled reusable guidance, decisions, pitfalls, product direction, workflow constraints, user preferences, current-state facts, and incidents.
- Do not store raw complaint text, assistant boilerplate, one-off test prompts, transient logs, raw transcripts, secrets, provider-internal product terminology, task-by-task summaries, Chat page prompts, Orchestrate/Plan mode-control text, or procedure-only runbooks better represented as agents/skills.
- Prompt wording for storage boundaries should stay abstract and product-neutral: describe durable contextual notes versus operational procedures without repeatedly naming or contrasting internal subsystems.
- Do not use repo-root `MEMORIES.md` as active task/chat memory. Static OpenVibely operating instructions belong in app-managed skills and selected managed memory. Repo-root `AGENTS.md` and `CLAUDE.md` are not loaded as supplemental provider instructions; use managed memory/skills instead.

Lifecycle behavior:
- Memory lifecycle work is owned by the built-in system Memory Curator agent through `recall_memory`, `update_memory`, and `consolidate_memory` lifecycle skills. Do not add separate memory-maintainer/consolidator agents, duplicate memory-maintainer skills, or seed migrations for a separate path unless explicitly requested.
- The model owns extraction and consolidation decisions. Go code should not replace this with hardcoded rule extractors, deterministic topic classifiers, or JSON proposal workflows when provider tool execution is available.
- Built-in `recall_memory` runs in the `route_task` phase with a `selected_memories` output contract, parallel to Skill Curator `selected_skills`. The worker passes `extras.available_memories`, populated only from `.openvibely/memories/MEMORIES.md`, analogous to `available_skills`.
- `recall_memory` should select useful memory identifiers/topics from that compact index and should not read topic memory-file bodies during recall. Enforce this structurally with hook-scoped tool filtering: route-phase `recall_memory` should not receive scoped file tools, while update/consolidation hooks still may. Existing stale `before_run/recall_memory` hooks should be repaired/removed so recall does not double-run after upgrade.
- Route-memory tool isolation is authoritative: `memory_curator` `route_task/selected_memories` uses a sanitized/no-tools direct-agent call so the lower LLM service cannot rehydrate scoped file tools, plugins, MCP tools, or provider/default tools from the full Memory Curator definition. Update/consolidation hooks still may receive scoped memory file tools.
- Normal task and task-thread follow-up executions consume managed memory through route-selected handles, not by appending raw memory files, all indexed memory content, or unresolved filename citations to the user prompt. Interactive Chat receives selected-memory handle context through `ChatSystemContext` via a recall-only lifecycle preparation path.
- Selected-memory prompt context is handle-only for skill-style parity: render compact verified handles, plus `memory_view` guidance, without Memory Curator-generated `summary`, `snippet`, `content`, or `topic` text. Lifecycle/debug views may keep route metadata, but task-facing `memory_view` returns only handle/file/body.
- `memory_view` is the canonical read-only request-scoped runtime tool authorized only for route-selected, indexed memory handles. It resolves files under `.openvibely/memories/` and rejects traversal, absolute paths/full `.openvibely/memories/...` paths, symlink escapes, unindexed handles, and unselected handles. Tool-capable API/OAuth Chat must expose `memory_view` in eligible Orchestrate and Plan modes even when generic filesystem/default coding tools are withheld; CLI chat transports may expose only native tools such as `Read` because they cannot receive OpenVibely request-scoped runtime tools. Selected-memory prompt guidance should explicitly tell the model to call `memory_view` when the user asks to view/read/load an authorized selected memory, rather than treating the handle listing as sufficient. Do not add compatibility aliases such as `view_memory` unless explicitly requested as product behavior.
- `memory_view` is also an explicit agent allowed-tool grant surfaced in the agent create/edit dialog. It should be default-enabled for new/generated agents and for the protected Memory Curator declaration, while agents that remove the grant should not receive the selected-memory runtime tool. This grant controls whether the final chat/task agent may load selected memories; it does not change Memory Curator route selection, `MEMORIES.md` filtering, or scoped-file memory curation tools.
- Route-selected memory handles are post-filtered against the app-generated `MEMORIES.md`/`available_memories` index before rendering selected-memory prompt context or authorizing `memory_view`; safe but unindexed hallucinated filenames must be dropped, matching selected-skill filtering against the skill catalog.
- 2026-06-06 live-chat incidents: OpenAI OAuth Chat Orchestrate turns for project `b184292efa07a415fc59967a5fc328d1` successfully ran Memory Curator and selected indexed memories, including `realtime_and_frontend_patterns.md`, but the assistant reported no `memory_view` or attempted denied default tools. Durable fixes are threefold: apply request `ToolFilter` to outgoing provider tool definitions, not only tool execution, so denied defaults such as `list_files`, `bash`, or `read_file` are invisible while allowed request-scoped `memory_view` remains available; route explicit Orchestrate/Plan streaming chat through the chat provider path even when `ChatHistory` is nil on a first turn; and register `memory_view` as a read-only `memory` capability in the chatcontrol Orchestrate/Plan action registry so those modes advertise it as an allowed tool. This applies to OpenAI Responses, OpenAI Completions fallback, Anthropic agentic request paths, and provider dispatch for first-turn chat. Lifecycle DB rows alone prove route selection/no-tools isolation but not the final provider tool surface.
- Later on 2026-06-06, a Chat Orchestrate request asking to call `memory_view` on `realtime_and_frontend_patterns.md` showed `memory_view` was callable but returned the selected-memory fallback because the handle was not selected for that turn. The durable fix is to honor explicit `memory_view("handle.md")` requests for exact handles already present in `MEMORIES.md`, merging those handles with Memory Curator route selections only when the lifecycle memory route hook ran for the turn. This applies to Chat Orchestrate/Plan recall-only lifecycle and normal task/task-thread lifecycle selected-memory authorization. A follow-up diagnosis and fix on task `fc45ace1353b52217abdb77a7403ebfb` covered an uncovered normal task lifecycle bug: explicit memory entries could be collected, then silently dropped because the merge/render/authorization branch was gated behind `haveSelectedMemories`. `PrepareLifecycleTurn` should preserve explicit indexed handles and authorize `memory_view` for them even when the route hook returns no `selected_memories` output, and task-followup regression coverage should protect that behavior. Full `.openvibely/memories/...` paths, traversal, `MEMORIES.md`, unindexed files, and arbitrary unselected files remain rejected.
- A separate 2026-06-06 semantic recall incident was fixed after task `2cda2bcdfd4eda24732924e34dec477c`: the prompt “Tell me about realtime front end patterns for this app” caused Memory Curator to select `realtime_and_frontend_patterns.md`, but downstream authorization could drop the selected handle because the real `MEMORIES.md` index used Markdown links with spaced titles such as `[Realtime and Frontend Patterns](realtime_and_frontend_patterns.md) - ...`. `IndexedMemoryHandles` must extract safe Markdown-link targets from `MEMORIES.md` and pass them through the existing clean-handle validation so route-selected Markdown-linked memories authorize `memory_view`. Selected-memory prompt guidance should also tell models to load relevant selected memories before relying on overlapping selected skills, repo inspection, or assumptions; skills such as `openvibely_htmx_templ_ui_workflow` may still be selected but must not replace memory recall. When a selected handle directly matches an app-specific question, such as `usage_analytics.md` for usage analytics, the final assistant should call `memory_view` before answering rather than merely acknowledging the selected handle or substituting source inspection.
- A 2026-06-06 task-thread follow-up incident on task `6e515ec37efa5fdcb70fca8141ca176b` showed Memory Curator repeated the original realtime/frontend selections when the user follow-up asked about usage analytics. Task-thread follow-up lifecycle routing must pass the current follow-up message as the effective `TaskPrompt` to `route_task`/`recall_memory`, while preserving the original task prompt only as contextual extra metadata such as `original_task_prompt`. Otherwise memory recall and skill routing can reuse stale first-turn topics and fail to select handles such as `usage_analytics.md` for the active turn.
- A separate 2026-06-06 follow-up recall diagnosis on task `fc45ace1353b52217abdb77a7403ebfb` found the opposite failure mode for terse or referential task-thread follow-ups: lifecycle routing may correctly use the current follow-up as `TaskPrompt`, but Memory Curator can return no memories because the original task prompt/thread context is only metadata and the `recall_memory` skill does not explicitly inspect it. Follow-up recall should balance both constraints: route on the current user message to avoid stale first-turn topics, while making original prompt/recent thread context explicit enough for referential follow-ups such as “continue,” “use that memory,” or debugging questions about the previous turn.
- A 2026-06-06 task-thread visibility incident on task `1c3cb95cecefedfa4ab009de13872d5f` showed Memory Curator selected `usage_analytics.md` for a follow-up turn, but the assistant later claimed the router provided no memories. Selected memory handles should be carried in request context alongside `memory_view` authorization and surfaced by `list_capabilities` as “selected memories for this turn,” so steering/debug questions cannot contradict lifecycle recall results. Capability reporting must also advertise `memory_view` itself when selected handles exist; otherwise a task-thread capability filter can list handles while hiding the only tool that can load them. Task follow-up runtime action tools must be built after lifecycle memory routing, or composed with the post-routing context, so closures such as `list_capabilities` see the current turn’s selected handles instead of stale pre-routing context. A later 2026-06-06 follow-up incident on task `9ddfd244efc9ea0edc293342fa4c6c35` showed the router selected `realtime_and_frontend_patterns.md` and `openvibely_architecture.md`, but final task-follow-up runtime filtering still omitted `memory_view` and could let the generic fallback handler shadow the scoped selected-memory executor. Another 2026-06-06 diagnosis on task `fc45ace1353b52217abdb77a7403ebfb` confirmed lifecycle DB rows selected memories for same-prompt task follow-ups before model execution, while the assistant still reported no memories; because the DB does not persist the fully assembled provider request, this points debugging after lifecycle selection, at context/tool propagation into the final task-follow-up provider call. The reliable verification boundary for “did selected memories reach the LLM?” is the normalized provider request/provider system prompt and the actual context JSON/tool surface visible to the final assistant, not lifecycle DB rows or post-hoc history inspection: `PrepareLifecycleTurn` should add selected-memory instructions, `combineAdditionalProjectInstructions` should carry them into `AgentRequest.ChatSystemContext`, and prompt builders should append that context before dispatch. When answering user debugging questions about which memories were suggested/selected or whether `memory_view` was available/called, distinguish evidence sources explicitly and do not claim the final assistant had or used `memory_view` based only on DB lifecycle records, task metadata, or selected-memory history. Tests should assert router-selected handles appear in model-facing context without requiring an explicit `memory_view` user request, while memory bodies remain absent until `memory_view` executes. Task-thread runtime tool filtering should include `memory_view` only when selected handles exist for that turn, and final composed runtime execution must route `memory_view` to the selected-memory executor rather than the fallback. When lifecycle has already installed the scoped selected-memory `memory_view`, task follow-up action-tool injection should not add a second chatcontrol placeholder `memory_view`; composite runtime tools should still de-duplicate names as a provider-safety backstop. This is visibility/execution ordering only: it must not broaden `memory_view` authorization beyond route-selected, indexed handles, and `memory_view` should stay hidden/fallback-only when no handles were selected. Later provider-bound log inspection for task `af8ef12f8b09a8ed4d81507e629470a9` confirmed the split: initial task turns can carry selected-memory handle context in `project_instructions`, while task-thread follow-up streaming turns carry it in `chat_system_context`; `chat_system_context` is part of the normalized provider request and is appended to the provider system prompt. Selected-memory bodies are not sent up front and should appear only after the model calls `memory_view`.
- On 2026-06-06, task `995331fd723856dd80ab2c9d683e8c00` prompted temporary `internal/service/llm_service.go` provider-boundary model-context dump logging for task-follow-up memory debugging. An audit-only review of squash commit `ef7151fba30114aec468979b38bdf471b42e6884` found that the temporary dump was still committed as unconditional `logTemporaryModelContextDump` calls for streaming/task provider requests, logging full user prompts, `ChatSystemContext`, `ProjectInstructions`, chat history, selected-memory handles, runtime tool names, and agent system prompts. The follow-up cleanup removed both dump call sites and the helper from `internal/service/llm_service.go`; future debugging should verify provider-bound context with targeted/test-only instrumentation or request snapshots, but never ship full model-context dumps in normal logs. Do not treat lifecycle DB rows alone as proof of final provider context; verify the normalized provider request/system prompt and actual tool surface visible to the final assistant. If the provider-bound context contains a relevant selected-memory block, `selected_memory_handles` includes the matching handle, and runtime tools include `memory_view`, then a skipped `memory_view` call is an assistant/model compliance failure unless provider logs show the tool was unavailable or rejected; do not keep treating that evidence pattern as a backend routing failure. API-level reproduction of task-follow-up memory behavior should use the user-facing worker/task-board path: create or queue a real active task, let the worker run the initial turn, then send the follow-up through the actual task-thread send/queued input promotion path. Do not use the `send_to_task` runtime tool as a substitute for UI/API task-thread follow-up behavior; it exercises a separate chat/action-tool path. Lower-level helpers such as direct `ExecuteTaskWithAgent` calls can intentionally bypass worker lifecycle preparation in tests and are not representative proof that task-board memory routing is missing. A later OpenAI OAuth-specific task-thread incident comparing Anthropic task `4c6719000f8c872be068947d689c6b69`, OpenAI task `fa2436ea39f24fdcaf3a8d296fa2e067`, and OpenAI Chat Orchestrate showed selected memory could still be lost after lifecycle preparation if the OpenAI provider adapter routed follow-up streaming requests through plain task streaming. The durable fix is to route follow-up requests with chat history or `ChatSystemContext` through chat streaming so `ChatSystemContext`, selected-memory guidance, and request-scoped `memory_view` reach the provider.
- Route hook index extras are scoped per output contract: `selected_memories` hooks receive only `available_memories` from `MEMORIES.md`, and `selected_skills` hooks receive only `available_skills`. Preexisting route index extras should be stripped before contract-specific injection so memory indexes stay out of Skill Curator route prompts and skill indexes stay out of Memory Curator recall prompts unless a future design explicitly requires cross-index routing.
- Direct managed-memory write tools should usually be reserved for memory-specific extraction/consolidation passes triggered by completion or scheduled runs, not global provider behavior.

Scheduled consolidation:
- Memory consolidation runs as a normal scheduled task assigned to the built-in Memory Curator agent with the `consolidate_memory` skill. Each project should get a real system-created scheduled task visible on the Schedule page like other scheduled tasks, while hidden from the normal Tasks board.
- Avoid hidden-run behavior, separate memory-specific schedule cards, parallel schedule tables, bespoke schedule status/history paths, prompt-display special cases, or special `LLMService` prompt/tool behavior when existing scheduler and task-thread features can represent the workflow.
- Bootstrap may create or repair the Memory Curator agent and schedule, but runtime execution should use the generic scheduled-agent path and generic `ScopedFiles` tool config for `.openvibely/memories` with read/write/delete permissions and default tools skipped.
- Use normal task/execution status, output, error, and alert mechanisms for scheduled consolidation results.
- Troubleshooting: if a completed chat/task produces no new memory file, first inspect memory run tables. If `memory_extraction_runs` has no row, the completion hook did not reach `RecordInteraction`; this differs from a successful extraction that decided there was nothing durable to save.
