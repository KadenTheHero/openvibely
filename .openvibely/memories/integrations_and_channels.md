OpenVibely has channel integrations for GitHub, Slack, Telegram, Discord, Email, and generic inbound webhooks. Integration UIs separate discovery/add flows from management cards, render explicit connection states, and keep destructive action language consistent as `Delete` with confirmation.

Durable channel direction:
- Supported channel integrations keep task-goal controls at parity with web/API chat where the surface supports them.
- Channel-origin Chat and task-thread behavior stays aligned with shared lifecycle, queueing, steering, cancellation, task-goal, agent-resolution, selected-memory, and swarm child follow-up routing rules. Canonical shared semantics live in `chat_thread_system.md` and `managed_memory.md`; this file stores integration-specific facts only.
- `internal/service/channel_chat_ingress.go` owns the reusable production inbound Chat flow for Slack, Discord, Telegram, and Email, including attachment staging/linking, model selection after downloaded/sniffed attachment classification, active-chat lookup/queue branching, first-turn task/execution creation, reply-context persistence, Chat Page broadcast, context/history assembly, runner invocation, and queued-chat promotion.
- Shared generic channel image validation, pending-session ID generation, unique temp filenames, MIME sniffing, and decoder imports belong in neutral channel ingress code rather than Slack/Discord/Telegram/Email-specific files.
- `internal/service/chat_action_runtime.go` centralizes generic channel runtime handlers for task creation/edit/execution, task goals, task thread viewing/sending, project switching/listing, schedule/personality/model/project utilities, channel completion, and shared alert/capability formatting.
- Slack, Telegram, Discord, and Email channel runtimes must handle advertised runtime tools through shared channel action handling. Channel-origin `create_swarm_task` creates real swarm parents with channel origin/context metadata and uses the active authorized channel project rather than any tool-supplied `project_id`.
- Attachment-bearing Chat turns should choose the model config after channel downloads and byte classification where bytes are available, so persisted execution or `thread_inputs.AgentConfigID` matches the runner/promotion config.
- Slack and Telegram runtime goal actions are wired through durable `TaskGoalService` behavior rather than surface-specific stubs.
- Channel-origin `switch_project` must run through channel-specific runtime tools, not only the generic chat runtime, so project selection persists under the correct channel identity. Slack, Telegram, Discord, and Email pass channel runtime tools into shared channel Chat ingress; these tools authorize the target project, persist active project for the channel user/sender, and return same-turn semantics where the current turn continues in its already-selected project context while future messages use the new selection.
- The shared runtime tool merge (in `processStreamingResponse`) gives channel-provided tools precedence over generic chat tools by name, then falls through to generic tools for any advertised tool a channel's partial runtime does not implement; this is how Email's `switch_project` persists under `email_sender_projects` via the Email-specific tool instead of being handled by the generic/informational chat implementation. Confirmed 2026-07-02 during Email `switch_project` authorization review.
- `send_message` is a first-class outbound channel runtime tool for Slack, Telegram, Email, and Discord. It sends through existing channel configuration/services, not duplicate credentials, and is backed by project-scoped saved outbound targets plus structured send-audit rows.

Outbound target facts:
- Outbound channel targets are distinct from inbound authorization allowlists. The default policy requires saved targets or a saved home target; arbitrary explicit targets require the project-scoped `send_message_allow_explicit_targets` setting.
- Saved outbound targets have durable `target_kind` values: `channel`, `user`, `chat`, or `email`. Slack/Discord user-DM destinations are first-class saved targets and route via `slack:user:<id>` / `discord:user:<id>` without depending on inbound Authorized Users.
- Backward compatibility remains: project-authorized Slack and Discord user IDs can still be used as outbound direct-message targets for that same project when no saved target exists, but non-authorized user IDs do not become outbound DM targets. A Slack/Discord user ID authorized in a different project must fail closed with a project-authorization error rather than falling through to explicit raw channel sending, even when explicit targets are enabled.
- In the Outbound Message Targets UI, `Home` marks a saved target as the default destination for that platform/project when a `send_message` request names the platform but not a specific saved target; it does not authorize inbound users or configure channel credentials.
- Outbound Message Targets is a permanent, always-visible safety-net card at the top of the Channels page. It behaves like other channel cards by opening editable controls when clicked, but the card itself must not expose delete/remove actions.
- The Outbound Message Targets edit dialog should match other channel dialogs with explicit Cancel and Save Settings footer actions. Dialog edits are staged: policy toggles, Add Target, and per-row Delete must not persist until Save Settings; Cancel, X, backdrop close, and ESC discard draft changes by reloading persisted state.
- The add-form target-type control should be platform-aware: Slack/Discord expose `Channel` and `User DM`, Telegram is fixed/labeled as chat/channel, and Email is fixed/labeled as email.
- Save Settings submits the full staged outbound-target list plus policy, reconciles it atomically for the project, closes the dialog on success, and refreshes the top card summary. Direct immediate add/delete outbound-target routes should not be exposed because they bypass the settings-dialog save contract.
- Per-target Test remains immediate and non-mutating. Draft targets can be tested before saving through a non-persisting draft-test path that sends only the fixed OpenVibely test message. Test progress/completion belongs inside the Test button rather than separate row banners or raw transport JSON.
- Outbound target names are optional. Multiple unnamed targets for the same project/platform are valid, while duplicate non-empty names remain invalid per project/platform and duplicate destinations remain invalid per project/platform/target-kind/target/thread.
- Outbound target reconciliation deletes omitted rows before upserting submitted rows so users can delete/save and later re-add the same destination without unique-constraint failures.
- Outbound Message Targets modal mutation fragments must stay modal-only and must not return the top-level card or `hx-swap-oob` card markup; the permanent top safety card refreshes separately after Save Settings.
- The shared Channels `htmx:afterRequest` JavaScript drives channel modal close behavior, webhook modal close behavior, and Outbound Message Targets close/reset behavior; request-path extraction must run before webhook/outbound branches and normalize query-bearing paths.
- The normal outbound-target save path enforces at most one Home target per project/platform by clearing existing homes before saving the new one. If duplicate homes are introduced outside the app path, `send_message` resolves the most recently updated home target.
- Outbound Message Targets handlers must enforce project ownership for saved target IDs. Save/update, delete, and test-send actions should only operate on targets owned by the resolved request project and should deny cross-project target IDs without dispatching messages or moving targets between projects.
- Outbound Message Targets per-target actions should preserve the displayed project context by including the displayed `project_id`, matching Delete/Add/Save/card refresh.

GitHub facts:
- Default/recommended auth mode is PAT (`github_auth_mode=pat`) for local/self-hosted OSS installs.
- GitHub App mode (`github_auth_mode=app`) is Advanced for cloud deployments.
- GitHub operation tokens are mode-specific: PAT mode uses the PAT directly; App mode mints ephemeral installation access tokens that are not persisted.
- Projects support both `repo_url` and `repo_path`. GitHub URL projects still use `repo_path` as the local managed clone path; `repo_url` is the remote source.
- Local Path availability is controlled by `OPENVIBELY_ENABLE_LOCAL_REPO_PATH`.
- GitHub URL mode clones into managed storage (`PROJECT_REPO_ROOT`, default `./repos`, Docker default `/data/repos`).
- GitHub URL project creation preserves configured PAT/GitHub App operation-token cloning, but fresh installs without a GitHub token fall back to local `git clone` so public repos and locally credentialed SSH/HTTPS private repos can still import.
- GitHub URL local fallback clones run non-interactively with `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=true`, and `SSH_ASKPASS=true`, matching other remote git operations so SSH/private-repo credential or host-key prompts fail clearly instead of blocking.
- GitHub URL project creation shows in-flight clone progress in the New Project create button with spinner text `Cloning repository...` while the HTMX create/clone request is active.
- Task Changes supports one-click PR creation, one PR per task, and reuse of existing task/remote-branch PRs.

Webhook facts:
- Inbound route is `POST /webhooks/inbound/:pathToken`.
- Webhook auth supports `X-Webhook-Secret` constant-time compare or `X-Hub-Signature-256` HMAC-SHA256.
- Each webhook call creates one active pending task with `created_via=webhook`.
- CRUD routes live under `/channels/webhooks`, including create, edit, delete, rotate-secret, and test.
- Backend template variables include `{{event_type}}`, `{{summary}}`, and `{{name}}`, though the UI may hide template fields.

Slack facts:
- Slack OAuth and manual bot-token modes are separate so switching modes does not wipe working credentials.
- Slack inbound behavior requires Socket Mode plus `app_mention` and `message.im` events; channel/private-channel/mpim screenshot and file-share delivery also requires `message.channels`, `message.groups`, and `message.mpim` subscriptions.
- Slack channel `message` events are processed only when they explicitly mention the configured bot, which preserves channel-noise filtering while allowing Slack `file_share` messages with `files[]` metadata to enter attachment ingestion.
- Slack screenshots/files require the Slack bot `files:read` OAuth scope; inbound file metadata is downloaded from Slack private URLs with the bot token and persisted through OpenVibely chat attachment storage. Slack file references can arrive in top-level `files[]`, message `attachments[]`, Block Kit image blocks with `slack_file`, or placeholder/file-ID-only objects that need `files.info` before download.
- Slack private file downloads need explicit bot-token `Authorization`, redirect handling that preserves auth only across trusted Slack file hosts, image-byte validation before provider calls, and fallback to Slack image thumbnail URLs when a primary private URL response is an HTML viewer/sign-in page. Do not send Slack bot-token auth to arbitrary external attachment/unfurl URLs.
- Authorized-user enforcement is project-scoped and allow-by-default when no authorized users are configured.
- Slack-origin Chat and `send_to_task` paths use the shared runner/queued task-thread implementation in production.
- Slack-origin queued Chat follow-ups stage file downloads into pending attachment sessions and persist `attachment_session_id` on `thread_inputs`, matching the shared queued attachment promotion path.
- Slack attachment storage is wired to the same configured uploads root used by chat attachment promotion.
- Slack attachment-bearing Chat live events should force the `/chat` page to refresh from server-rendered state after attachment rows are persisted, rather than appending a text-only synthetic live bubble, so Slack-origin screenshots appear like web chat uploads. Current known blocker: promoted queued Slack attachment Chat turns can publish the final `ChatNewMessage` without `HasAttachments=true` after attachment-session promotion, causing the live `/chat` UI to replace the queued row with a text-only synthetic bubble until manual refresh.
- Slack outbound `send_message` sends via the configured Slack bot token and supports saved channel IDs plus optional thread timestamps. Saved user-kind outbound targets and `slack:user:<id>` references resolve to direct messages by opening a Slack DM first without requiring the user ID to be in Authorized Users. Slack OAuth should include `im:write`; existing tokens may need reinstall/reauthorization if Slack returns `missing_scope`.

Discord facts:
- Discord is a first-class bot/gateway channel integration with Settings configure/test/delete UI, migrations, docs, and `github.com/bwmarrin/discordgo` as the Discord client dependency.
- Discord authorized-user enforcement is project-scoped and deny-by-default: users must be explicitly allowlisted before Discord-origin messages can create Chat turns or task-thread follow-ups. Authorized-user entries must use numeric Discord user IDs copied with Developer Mode, not usernames or display handles.
- Discord inbound behavior supports direct messages and bot-mentioned guild/channel/thread messages. Non-DM Discord messages must mention the bot; default channel IDs, free-response channel allowlists, and a configurable require-mention toggle are intentionally unsupported/ignored.
- Discord project switching persists active project selection per Discord user in `discord_user_projects` and reloads it for later messages, matching Slack/Telegram project switching semantics.
- Discord inbound attachments are supported through the shared chat attachment pipeline: Discord CDN/media downloads are trusted-host validated, image attachments are persisted for provider calls, duplicate filenames are made distinct, and attachment-bearing queued Chat turns stage pending attachment sessions.
- Discord replies preserve channel/thread/message/user metadata for queued promotion and completion callbacks. Initial Discord Chat turns pass reply context into the shared channel chat runner, and stored chat context tracks the bot acknowledgement message so the final response can edit the `Thinking...` acknowledgement.
- Discord-origin Chat and `send_to_task` paths use the shared runner/queued task-thread implementation in production, including task-goal controls and selected-memory/action-runtime parity with other supported chat channels.
- Discord outbound `send_message` uses the shared Outbound Message Targets channel-control model and saved/explicit/home target policy. Saved Discord targets use `target_kind=channel` for channel IDs plus optional thread IDs and `target_kind=user` for direct-message user IDs; thread IDs are outbound destination channels, not reply message IDs.
- Discord user IDs and channel IDs are both numeric snowflakes, so format alone cannot distinguish them. A bare numeric target resolves only as a saved target or as a project-authorized user DM by creating/using a Discord DM channel first; it must not fall through to raw channel send. Unsaved explicit Discord channel sends use `discord:channel:<channel_id>` or `discord:channel:<channel_id>:<thread_id>` when explicit targets are enabled.
- Discord inbound authorized-user allowlists remain separate from outbound saved targets and home-target policy except for the explicit direct-message convenience for project-authorized user IDs.
- Discord REST token validation only proves the token is valid; bot online/offline state depends on the Gateway websocket being open. Connection status and Channels UI should treat Discord as connected only when the Gateway is running, surface the last Gateway start error when configured-but-offline, and log configure-time reload/start failures while still treating persisted settings as a successful save response.
- Deleting the Discord channel clears the current project's Discord authorized-user allowlist along with Discord settings, so recreating the channel starts from a clean inbound authorization state.
- Discord's authorized-user Add/Delete controls are embedded inside the Discord settings modal but remain independent HTMX fragment updates. They should update `#discord-authorized-users` without closing the modal or saving Discord settings; the main Save Discord action closes via the shared path-based afterRequest listener.

Telegram facts:
- Telegram attachment and command behavior remains project-aware.
- Telegram services can be created at startup or from Settings; both paths need equivalent shared-runner, AgentRepo, and queued-promoter wiring.
- Telegram-origin Chat and `send_to_task` paths use the shared runner/queued task-thread implementation in production.
- Telegram queued Chat turns delete staged pending sessions if `thread_inputs.CreateQueued` fails after attachment staging; execution attachment linking should use the shared rollback/error-returning helper.
- Telegram cleans downloaded temp attachments on post-download failures for model selection, active-chat lookup, chat task creation, and execution creation, and classifies vague `application/octet-stream` PNG/JPEG/WebP/GIF bytes as images instead of text context.
- Telegram outbound `send_message` sends via the configured bot and supports saved chat IDs plus optional topic/thread IDs.
- Telegram `Start`/`Stop` is nil-safe for partially constructed/test services.
- `TelegramService` lifecycle (`Start`, `Stop`, `UpdateToken`) is serialized end-to-end through a single `lifecycleOpMu` operation mutex so concurrent calls cannot interleave; `UpdateToken` holds that lock across stop → create new bot → assign → start. A separate `runDone` channel represents the actual upstream `GetUpdatesChan` poller lifetime (closed only after the library's updates channel drains), so `Start`/relaunch is refused while an old poller is still draining and `UpdateToken` waits for (or times out/errors on) full drain before starting the replacement poller. This prevents duplicate `getUpdates` pollers and the resulting Telegram `Conflict: terminated by other getUpdates request` error.
- Telegram Rich Messaging V2 is a default-on channel setting (`telegram_rich_messages_v2`) exposed in Settings, persisted on save, and cleared on delete; existing Telegram channels with an absent/blank setting resolve as enabled unless the user explicitly saved `false`.
- When Telegram Rich Messaging V2 is disabled, outbound sends/edits use normal Bot API `sendMessage`/`editMessageText` with fully escaped `MarkdownV2` text first, then retry as raw plain text with no parse mode if Telegram rejects MarkdownV2; this preserves literal markdown characters rather than rendering OpenVibely markdown styling.
- Telegram rich outbound delivery uses Telegram rich API payloads for sends/edits/drafts, with MarkdownV2/plain fallback only for clear rich API rejection; ambiguous transport errors should not fall through to another visible delivery path because that can duplicate messages.
- Telegram final placeholder delivery prefers rich edit, then tries a separate rich final send only after clear rich edit rejection; ambiguous rich edit or rich send transport errors stop rather than taking another visible delivery path.
- When Telegram final placeholder rich edit is clearly rejected and a separate rich final send succeeds, the original `⏳ Thinking...` placeholder is edited away to a short completion marker so users do not see a stale acknowledgement beside the final response.
- Telegram rich draft streaming must survive the inbound handler returning after handing work to the shared runner, so preview loops cannot depend on the short request context.
- Telegram preview streaming and final delivery are coordinated per acknowledgement message: final delivery stops the active preview before posting final output, legacy terminal previews render clean text without `_Generating..._`, and rich-mode finalization must avoid duplicate visible response surfaces.
- Telegram rich drafts are preview updates, not the persisted final response. After draft previews, final rich delivery should persist when required by the Bot API/runbook, then clear/edit away the original placeholder without falling through after ambiguous rich errors.
- Telegram visible rich-draft preview state must survive preview goroutine exit, including terminal-execution exit, until final delivery consumes it. This prevents final delivery from forgetting a draft was visible and re-entering placeholder edit/send paths that can duplicate output.
- When a visible Telegram rich draft exists and final rich delivery is clearly rejected, final delivery should provide a persisted MarkdownV2/plain fallback and then clear/edit away the original placeholder. Ambiguous transport errors should still stop before another visible path to avoid duplicates.
- Telegram Desktop for macOS 12.8 can crash while rendering Rich Messages V2 payloads whose raw markdown starts as a GitHub-style pipe table; Android may render the same payload without crashing. The user objected to an automatic table-fallback workaround, so do not assume routing table responses away from Rich V2 is desired unless explicitly re-approved; prefer a less intrusive/sanitized fix if needed.

Email facts:
- Email is a first-class channel integration: it supports IMAP inbound polling, SMTP outbound replies, provider presets, settings UI, project-scoped authorized sender management, and inbound attachments.
- Email-origin Chat and task-thread follow-ups use the shared runner and durable `thread_inputs` queueing/promotion path like Slack and Telegram.
- Email reply context is durable: queued thread inputs and email-origin chat tasks preserve message/thread headers so SMTP responses can keep the email conversation threaded after async promotion or completion.
- Email Chat sessions are scoped by normalized sender plus thread root/message ID, falling back to a subject hash when threading headers are absent; active-chat detection and replay history should not collapse all mail from one sender into one global chat.
- Email authorized-sender enforcement is project-scoped and deny-by-default, unlike Slack's allow-by-default empty-authorized-user behavior.
- Email sender normalization extracts the mailbox address from RFC/display-name strings before lowercasing. Email project switching authorizes against the target project's Email authorized-sender configuration using that normalized mailbox address, persists active project selection per normalized sender in `email_sender_projects`, and re-validates authorization before using a saved project; if the saved project is missing or no longer authorized, Email falls back to scanning authorized projects.
- `repository.NormalizeEmailAddress` (`internal/repository/email_auth_repo.go`) is the single shared normalizer backing Email authorized-sender checks, `email_sender_projects` persistence/lookup, session keys, and self-sender checks. It previously only trimmed/lowercased input, so RFC display-name senders like `Name <mailbox@example.com>` were compared/stored literally against the mailbox-only allowlist entry, causing false "email sender is not authorized" errors on `switch_project` even when the mailbox was correctly configured. Fixed 2026-07-02 by parsing with `net/mail` to extract the mailbox before lowercasing; keep this normalization centralized rather than reimplemented per call site.
- Audited 2026-07-03: saved-project revalidation and fallback-to-scanning-authorized-projects behavior for Email active project selection was already correct in the service layer; the display-name normalization fix above was the only defect. Regression coverage was extended for saved authorized project usage, saved unauthorized project fallback, and session identity normalization (display-name senders resolve to the same `email_sender_projects` row as mailbox-only senders) using non-private `example.com` addresses in `internal/repository/email_auth_repo_test.go`, `internal/repository/email_sender_project_repo_test.go`, and `internal/service/email_service_test.go`.
- This same normalization gap and root cause were independently re-traced and re-fixed in separate swarm-worker worktrees on 2026-07-03 (tasks `f331f990f2c0cefd640ff2cf2e161929`, `c6fa00045c09e98c982c6a2d469ec3ce`, and `30ce00bda5e1382f48a50dc14af990f3`), all again touching `internal/repository/email_auth_repo.go` (using `net/mail.ParseAddress` to extract the mailbox before lowercasing) plus regression tests in `internal/repository/email_auth_repo_test.go`, `internal/repository/email_sender_project_repo_test.go`, and `internal/service/email_service_test.go`. - Email preset-provider app passwords are normalized by removing whitespace on save and runtime load so Gmail-style grouped app passwords work; custom provider passwords preserve internal spaces.
- Email Settings use the shared masked secret input behavior for app passwords: the saved value is rendered into the password field so the eye toggle can reveal/hide it, and leaving it blank on save preserves the stored secret.
- Email authorized-sender controls are embedded inside the Email settings form, so the UI posts and handlers accept the sender address as `authorized_email_address`; this avoids colliding with the channel account `email_address` field. Authorized senders must be persisted only by the explicit Add button path; typing an address and clicking Save Email Settings must not add it.
- Email settings booleans in the channel dialog should use DaisyUI toggle styling, matching Telegram's modal toggles, while preserving normal checkbox form submission semantics.
- Email outbound `send_message` sends new SMTP email through the existing Email channel configuration, without `In-Reply-To`/`References`; optional tool/default subjects are explicit and blank subjects default conservatively.
- Email inbound attachment parsing decodes MIME attachment parts, carries them on inbound messages, honors `email_skip_attachments`/`SkipAttachments`, byte-sniffs/validates staged files like other channels, and wires Email through shared chat ingress attachment options for model vision selection, first-turn execution linking, queued `thread_inputs.attachment_session_id` pending sessions, and text-attachment context.
- Attachment-bearing emails with empty bodies should not be dropped; empty-body/no-attachment messages remain ignored. Email uses the same uploads root and chat-attachment repository wiring as other attachment-capable channels.
